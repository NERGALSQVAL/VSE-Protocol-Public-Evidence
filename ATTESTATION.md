# 01 // Purpose

VSE Protocol is designed to transform authenticated renewable-energy production data into immutable, single-use, machine-verifiable digital energy proofs.

The protocol does not treat manually entered values, spreadsheets, screenshots, user declarations, or self-reported production totals as authoritative energy evidence.

```text
PHYSICAL ENERGY ASSET
        ↓
MANUFACTURER-AUTHORITATIVE DATA SOURCE
        ↓
VSE RAW EVIDENCE CAPTURE
        ↓
CRYPTOGRAPHIC HASH
        ↓
DETERMINISTIC VALIDATION
        ↓
ENERGY CALCULATION
        ↓
AUDIT CHAIN
        ↓
VSE UNIT
        ↓
MINT
        ↓
ALLOCATION / SALE
        ↓
RETIREMENT
        ↓
FINAL PROOF
```

# 02 // What VSE Attests

For every valid VSE proof, the protocol is intended to attest that:

1. The underlying production evidence originated from an approved machine-authoritative source.
2. The raw source response was captured before proof creation.
3. A cryptographic fingerprint of the raw evidence was calculated by VSE.
4. The source identity and relevant device metadata passed protocol validation.
5. The production interval passed timing and duplicate checks.
6. The energy quantity was calculated according to the active VSE methodology.
7. The resulting verification state was linked into the VSE audit chain.
8. The same source evidence and production interval cannot be repeatedly accepted as new energy.
9. A VSE Unit cannot be treated as available after final retirement.
10. The final proof can be independently checked against the recorded cryptographic state.

---

# 03 // Authoritative Source Requirement

VSE accepts only data associated with an identifiable physical energy asset and retrieved through an approved machine-authoritative path.

Accepted paths may include solar inverter telemetry, smart-meter telemetry, approved hardware telemetry systems, official manufacturer infrastructure, and authenticated manufacturer cloud or OpenAPI access representing data generated by the underlying physical device.

**Not accepted as primary production evidence:**

- manual UI entry;
- spreadsheets;
- user-uploaded CSV production totals;
- screenshots;
- human declarations;
- manually edited payloads;
- unverifiable third-party production totals.

If the source cannot satisfy the active VSE source-verification rules, the evidence is rejected.

---

# 04 // Raw Evidence & Cryptographic Integrity

VSE follows an evidence-first model.

The protocol is designed so that source evidence is captured before a verified unit is created. For accepted evidence, VSE calculates its own cryptographic fingerprint.

Where additional cryptographic mechanisms are available, the protocol may also verify authenticated requests, signatures, HMAC values, or equivalent integrity controls.

> **A supplied hash is not trusted merely because an external party claims it is correct.**

VSE independently calculates and validates the cryptographic state.

---

# 05 // Deterministic Validation

The same valid source evidence, processed under the same methodology and protocol version, should produce the same verification result.

Validation may include source identity, plant/inverter/logger/meter identifiers, source timestamps, interval boundaries and ordering, duplicate detection, missing or invalid samples, excessive sampling gaps, future timestamps, source-response integrity, previous audit state, and methodology version.

> **A human operator must not be able to convert mathematically invalid evidence into valid evidence.**

---

# 06 // No Human Override of Failed Evidence

Administrative access does not grant production authority.

Administrators may manage operational functions, users, organizations, access control, contracts, billing, support, or review workflows.

Administrators must not be able to:

- fabricate renewable-energy production;
- manually approve failed source evidence as valid;
- rewrite accepted audit history;
- mint unsupported energy;
- bypass duplicate protection;
- restore a finally retired unit to active inventory.

Human review may exist for compliance, investigation, support, security, legal review, or enterprise assurance, but it must not rewrite the underlying machine evidence.

External review may assess implementation quality, security, smart contracts, or the legal environment. It does **not** determine or override the mathematical validity of an individual VSE proof.

---

# 07 // Audit Chain

Accepted verification events are linked into an append-only audit history.

> ## NEW INFORMATION CREATES NEW STATE.  
> ## IT DOES NOT REWRITE OLD STATE.

Corrections, investigations, exclusions, and security actions should create new auditable events rather than silently modifying historical evidence.

---

# 08 // Duplicate & Double-Use Protection

VSE is designed to prevent the same underlying renewable-energy production from being represented repeatedly as new verified energy.

Duplicate protection may operate across source evidence hash, source identity, production interval, audit identifier, VSE Unit identifier, blockchain registry state, and retirement state.

A previously accepted interval must not become new inventory merely because it is resubmitted through another user, organization, API key, request, or transaction.

---

# 09 // VSE Unit Model

A VSE Unit is a verification instrument, not a general-purpose transferable cryptocurrency.

The intended registry model is:

- only authorized VSE infrastructure may mint;
- units remain under VSE-controlled registry ownership;
- no unrestricted transfer mechanism;
- no public secondary market;
- no arbitrary approval mechanism;
- duplicate source / audit / interval minting prohibited;
- retirement allowed only once;
- retired state is final.

The blockchain layer is used as part of the verification and finality architecture. It is not the source of the renewable-energy measurement itself.

---

# 10 // Retirement & Finality

Retirement represents final use of a verified VSE Unit.

A finally retired unit must not return to available inventory, be sold again, be retired a second time, be reactivated, or be silently reassigned to another beneficiary.

A retirement record may cryptographically bind the unit to a beneficiary, purpose, sale or allocation, retirement transaction, methodology, and protocol version.

> **RETIREMENT IS FINAL.**
